# AlembicAgent Atlas 现状分析与后续方案

日期：2026-10-23。下文保留**批准前的评估与原方案**；用户已随后确认实施，最新状态与验收见[实施结果](2026-10-23-implementation.md)。

本方案只面向 Agent 的独立图谱。它不创建 Wakeflow 任务、不授权产品运行时修复，也不改变 Core 或宿主仓库的职责。量化依据保存在 [本次评估记录](2026-10-23-assessment.json)；v4 的原始记录仍保存在 [历史验证报告](../evidence/iterations/v4-validation.json) 和不可覆盖快照中。

## 1. 核心判断

Atlas 已经建立了可用的架构文档、源码索引、可控执行样板和版本留档基础。后续价值最高的工作是让这些材料持续对应正在演进的代码，并让读者从一个问题找到具体结论、证据和下一步。

当前首要问题是**来源漂移**。v4 的通过结论属于当时的输入；今天不能直接沿用“293 个源码全文审阅、267 次执行通过”的表述来描述当前代码。维护机制需要把历史成果、当前可继承部分和待复核部分同时呈现。

建议顺序：**V5 校准当前基线 → V6 建立精确证据关联与增量维护 → V7 完成故障、文件和接入阅读路线**。版本号是拟议里程碑，不是已经产生的新快照。

## 3. 现有基础值得继续保留

1. **13 专题按工程问题组织。** 每个专题已有职责、调用、直接依赖三类基础视图，适合继续作为信息架构主干。
2. **两条完整纵切已建立。** “请求到工具回执”和“分析发现到知识候选回执”能承载后续全部关联机制的样板。
3. **事实种类有基本区分。** 静态导入、人工调用说明、工具回执、浏览器渲染、Core／宿主边界没有被统一成一个成功标记。
4. **证据已有输入绑定。** 文档、样板、定向执行和图源已有指纹检查；当前性检查正确暴露了本轮漂移。
5. **读者和历史数据已有隔离。** 搜索、图形缩放、直接依赖探索、来源弹窗、历史按需加载和失败显式呈现均可沿用。

内容深度并不均匀：56 页中 L0 为 3 页、L1 为 14 页、L2 为 27 页、L3 为 7 页、L4 为 5 页。18 个补深文件拥有结构化分段和失败说明；此前继承的全文记录不能被解释为每个文件都有同等详细的说明。后续应按读者问题和风险补充内容，不按专题平均分配页数。

## 4. 主要缺口与原因

### 4.1 知道“过期”，还不能直接知道“该复核什么”

现有检查可判断指纹变化，但缺少变动文件、受影响图边、结论、测试与重审决定之间的完整清单。一个输入缺失还可能产生大量级联消息。维护者仍需人工把错误列表重新组织成工作顺序。

所有定向组都包含 `src/**/*.ts`，39 个 v4 组还包含全部测试和相关脚本。它们的失效判断安全而保守，但无法指导精确重跑。本次变动横跨 Runtime、Memory、AI 和 Tool，实际验证范围可能仍很广；不能预先承诺只跑少量用例。

### 4.2 有记录，缺少部分严格约束

`scripts/evidence.mjs#validateScopedExecutionShape` 验证标题、状态和计数，却没有强制完整用例身份、采集位置、命令与时间等字段。主审做了一个纯内存反例：复制同一个用例并同步增加 passed 数，验证器仍返回空错误列表。这是校验能力缺口，不表示历史结果失实。

`readings.json` 的加载只要求路径、哈希为字符串，尚未严格校验阅读深度、路径唯一性、继承来源和审阅材料关联。原始阅读成果应保留，同时补齐可检查的来源链。

### 4.3 全局执行数字难以回答某条结论是否被验证

`src/main.ts#sideEvidence` 在不同页面展示同一批全局定向执行总数。逐边表里又有手工书写的“本轮通过／未执行”说明。需要把页面、结论、精确断言和实际执行绑定起来，减少多处手写状态。

### 4.4 读者仍要在长文中自行寻找故障

失败信息已经很多，但主要位于长表和专题正文。当前路由只有 home/doc/files；搜索是字符串包含匹配，最多返回 12 篇文档和 24 个文件，没有匹配段落、场景筛选或稳定的故障入口。

跨文档链接的 fragment 会在改写路由时丢失，h2 的 ID 又按渲染顺序生成。稳定段落定位应先于故障索引和搜索增强。

### 4.5 文件说明尚未充分利用已有数据

阅读记录已有 `flow/tests/reviewPage`，但 `browser-data.mjs#browserReading`、浏览器 `Reading` 类型和来源弹窗未投影这些字段。读者从文件进入后能看到职责和相关页面，却还不能直接到达其行为、失败分支与验证。

## 5. 后续 Atlas 应帮助读者完成什么

| 读者问题 | 应走通的路径 | 优先级 |
| --- | --- | --- |
| 今天哪些说明仍可沿用？ | 采样身份 → 新改删输入 → 受影响结论 → 重审决定 → 新证据 | P0 |
| 这条架构结论根据什么成立？ | 结论／图边 → 源码位置 → 具体断言 → 实际执行 → 输入与替身边界 | P1 |
| 出现 timeout、partial 或某诊断码后怎么办？ | 症状 → 所处阶段 → 已确认／未知副作用 → 恢复责任 → 证据 | P1 |
| 修改某文件前要先看什么？ | 文件／符号 → 行为链 → 消费者 → 相关失败场景 → 验证项 | P2 |
| 宿主怎样正确接入 Agent？ | 公开入口 → 必需注入 → 最小输入 → 结果判断 → 错误与释放责任 | P2 |

优先用现有两条纵切验证这些路径，然后扩展到其余专题。新增入口不要求新增一套事实正文。

## 6. 数据与内容设计

继续保持本地独立子包和 Markdown/Mermaid 正典。新增结构化记录承担身份、关系和状态，不复制整段说明。

| 对象 | 应保存的最小信息 | 约束 |
| --- | --- | --- |
| 输入身份 | HEAD、工作树输入清单与哈希、采样时间、配置身份 | HEAD 相同也可能有未提交变化；时间不能代替内容身份 |
| 阅读记录 | 文件哈希、阅读深度、复核范围、原始／继承记录、对应文档 | 字节未变可继承；变化后先复核，不能只改哈希 |
| 结论／图边 | 稳定 ID、关系类别、成立条件、源码和断言引用 | import、call、data-flow、ownership、state-transition 分开；并列依据不写成调用箭头 |
| 失败场景 | 稳定 ID、症状／诊断码、正文锚点、关联结论与验证需求 | 副作用和恢复说明保留单一正文；不把已退役入口继续标为当前风险 |
| 执行记录 | 命令／筛选、采集集合、精确 case、runner/harness、前后输入摘要、结果摘要 | 用例序号只在对应采集集合内有效；相同显示标题不代表同一个参数实例 |
| 当前关联 | 本页／本结论引用哪些执行；哪些过期、未覆盖、历史或已退役 | 全局累计数保留在总览，不能代替本页验证 |
| 封存版本 | 文档、库存、关系、阅读与执行的自一致清单 | 原历史不覆盖；旧 schema 保留旧证据等级，不补造缺失字段 |

原 27 条 v3 执行记录缺少 v4 后补的完整身份字段，宜保持“旧版身份记录”。不能根据标题猜出其参数实例。新规则要求精确身份时，应重新执行或明确其不能满足该等级。

快照保存了文档、库存和哈希，并不等同于保存所有未提交源码的可恢复副本。可重放性设计应优先记录可解析的 Git blob／提交来源；缺少原始源码时明确说明限制，避免把一次阅读快照宣称为完整源代码备份。

### 四种状态始终分开展示

- **来源状态：**匹配、变化、缺失、未采样。
- **阅读状态：**已全文／局部／仅索引，以及原始还是继承记录。
- **执行状态：**未执行、通过、失败、中止；输入是否匹配另列。
- **图形状态：**图源与 renderer 下的回执是否匹配。

浏览器默认只承诺采样时点。静态导出无法自己知道外部仓库后来是否变化；页面应明确“截至哪次采样”，通过显式重新采样获取新状态。首页“专题就绪”等文案也要区分已编目与已复核。

## 7. 分期落地方案

### V5：校准当前基线，形成可维护的同步版本

**目的：**让今天阅读 Atlas 的人知道当前实现、已退役表面和未验证部分。

实施顺序：

1. 在 Atlas 内建立当前状态／变更清单输出，复用现有采集和指纹函数。区分缺输入、坏锚点、图源变化和执行输入变化，聚合主要原因而不丢原始诊断。
2. 按责任链复核 113 个变化源码、1 个新增源码及 4 个删除对象。176 个字节一致的旧阅读保留来源，不强制重读。
3. 先校准消息与宿主、Memory 快照、旧策略与工具合同退役，再处理 Provider 合同、来源感知脱敏及相关预算／Hook／状态变化。每个对象记录保留、修正、退役、待核验之一。
4. 更新受影响的正文、边表、输入列表、公开入口和文件索引。先确认真实调用与测试断言，再更新指纹。
5. 核对并重跑两条纵切的当前接线，以及仍被当前文档声称覆盖的相关场景。因产品合同变化需要调整的测试采集／fixture 只放在 Atlas 内，不修产品实现。
6. 校准当前与历史的显示文案，分别列出新增执行、复用、已退役与待验证项。全部条件满足后才封存新的 v5。

**验收条件：**

- 当前库存的新、改、删对象都有去向，退役文件不再被当前调用链引用；v4 保持原样。
- 当前内容的缺失路径、缺失符号／测试、错误直接依赖和未处理的来源漂移归零。
- “当前通过”的执行必须绑定当前输入；未重跑的旧记录保持历史状态。不能为了检查变绿而删除失败／过期证据或缩减原有行为闭环。
- 六场景样板仍完整；知识纵切继续区分工具成功、领域 outcome、created、readiness 和宿主发布。
- `check:current`、必要的图形复验、Atlas 自有检查和构建通过，产品文件与用户改动保持。

### V6：精确证据关联与增量维护

**目的：**源码再变化时，能找出需复核的结论和验证，而不靠重新阅读所有页面。

实施顺序：

1. 先为重复 case、错误采集序号、标题与集合不匹配、缺执行身份、坏阅读来源等情况写反例，再强化版本化 schema。
2. 把定向执行采集过程放入 Atlas 自有脚本，保留原始规范化结果摘要和命令。避免只有临时脚本能复现某份记录。
3. 为两条纵切建立最小结论／场景／断言关联，右侧证据栏按页和选中边显示；全局数字保留在总览。
4. 输出“变动输入 → 阅读记录 → 文档／结论 → 相关测试 → 是否需重渲染”的维护清单。
5. 在能完整说明测试、fixture、配置、harness 与外部公开依赖的前提下收窄输入范围。动态边、全局配置和不确定依赖继续采用保守失效。
6. 增强快照读取时的自一致校验，保留旧版兼容解释。内容摘要用于检查一致性，不宣称提供外部签名或不可篡改保证。

**验收条件：**

- 同一个采集身份重复出现即拒绝；显示标题相同但参数实例不同仍可正确区分。
- 坏阅读深度、重复路径、无效继承来源或失效文档关联可被检查发现。
- 页面没有相关执行时，不能因全局通过总数而暗示“本页已验证”。
- 改一个局部 fixture、一个共享 Runtime 文件、一个全局配置，分别产生有理由的影响集合；未知依赖不会悄悄保绿。
- 仅修改 prose 不使产品测试自动失效；修改 Mermaid 使对应图形回执失效；修改源码使相关结论进入复核。
- 旧记录可读、旧快照不回退到当前证据；缺少完整身份的历史记录不被自动升级。

### V7：按故障、文件和宿主任务阅读

**目的：**减少读者为理解一个问题而横跨长表反复搜索。

实施顺序：

1. 增加稳定段落／场景锚点，跨页链接保留目标；兼容现有页面 URL。锚点不依赖 h2 的排列序号。
2. 从已校准的失败记录中选至少六个高价值场景作为入口：回执后观察失败、取消／超时与部分结果、HOST 诊断的实际来源、创建确认后 readiness 降级、scope 释放责任、来源感知脱敏边界。
3. 场景页展示触发、阶段、已确认与未知副作用、恢复责任、重试前提和证据，不新增一份平行的故障事实正文。
4. 在文件页／来源弹窗使用已有 `flow/tests/reviewPage`，把直接语义引用排在广域输入闭包引用之前。
5. 搜索返回命中片段、类型、来源状态和稳定段落链接；仍保持有界结果并显示省略数量。
6. 串联宿主接入路线：入口、必要注入、最小输入、结果判断、错误和释放责任。涉及真实宿主验收时另行界定任务范围。

**验收条件：**

- 六个典型症状均无需先知道内部文件名，就能定位到确切说明和证据。
- 读者可以回答“工具是否执行、写入是否确认、能否重试、由谁读回”。未验证部分保持可见。
- 以 AgentRuntime、MemoryCoordinator、terminal 三个文件完成修改前阅读路线，能直接到达对应行为和测试。
- 重排标题后链接仍有效；历史版本缺场景时明确缺失，不跳到当前替代内容。
- 桌面与窄屏完成代表性阅读任务；依赖图仍明确标为静态关系，不生成未经验证的动态调用图。
